# 工具链与运行时

这一章说明 Csay 现在怎样编译、两个编译器怎么选、内存由谁管理，以及“换成 C# / CoreCLR / 热更新”意味着什么。它不是承诺这些后端已经存在，而是把边界讲清楚。

## 当前编译流程

Csay 的默认工具链是：

```text
.csay 源文件
  → TypeScript 编译器（src/）
  → C 代码（build/*.c）
  → 系统 C 编译器（clang / gcc / 随包 TCC）
  → 原生 exe
```

TypeScript 编译器运行在 Node.js 22+ 上，负责词法、语法、类型检查、泛型展开、`引` 多文件加载和 C 代码生成。生成的 C 代码依赖 `selfhost/csay_runtime.h` 中的运行时，包括文本、列表、表、异常、文件和区域分配。

Windows 发布包里带有 TCC，所以用户不需要另装 C 编译器。`--fast` 使用 TCC，编译快、优化少；`--debug` 生成 `#line` 映射并传 `-g`；`--project` 读取目录里的 `主.csay` 并递归加载 `引` 依赖；`--format` 只格式化入口文件。

## 源码怎样拆分

默认编译器已经按职责分成多个 TypeScript 文件：`lexer.ts`、`parser.ts`、`checker.ts`、`generics.ts`、`codegen.ts`、`runtime.ts`、`loader.ts` 和 CLI。内建函数名集中在 `src/stdlib.ts`，语义检查不再维护第二份名单；具体 C 实现仍在 `runtime.ts`，代码生成仍在 `codegen.ts`。

C 运行时头文件 `selfhost/csay_runtime.h` 由 `src/runtime.ts` 生成，不能直接手改；改运行时后要重新运行导出脚本并重建自举编译器。

自举编译器 `selfhost/编译器.csay` 目前仍是单文件。它保存了大量编译期全局状态（类型表、类成员、输出缓冲、当前区域），而自举阶段的 `引` 还没有把这些状态跨文件组织起来的机制；贸然拆开会让固定点构建更难定位。当前优先保证“能编译自己”，默认编译器则承担可维护的模块化。等自举编译器支持更完整的模块/全局状态后，再按词法、语法、生成拆成多个 `.csay` 文件。

## 默认编译器与自举编译器

仓库里有两个编译器：

| | 默认编译器 | 自举编译器 |
|---|---|---|
| 源码 | `src/*.ts` | `selfhost/编译器.csay` |
| 运行方式 | Node.js | 编译成原生 exe |
| 覆盖范围 | 全部语言特性、`引`、项目构建、测试、格式化、调试 | 语言核心与大多数运行时特性，单文件编译 |
| 主要用途 | 日常开发、发布、工具链 | 验证语言能编译自身 |
| 构建 | `node src/cli.ts` | `node tools/自举.mjs` |

自举编译器的意义是“用 Csay 写 Csay 编译器”，证明语言足够表达复杂程序，而不是替代默认工具链。自举固定点测试要求 Stage 2 和 Stage 3 生成的 C 完全一致；这能发现默认编译器里的隐藏假设。

日常使用默认编译器：

- 需要 `引` 多文件、`--project`、`--test`、`--format`、`--debug` 时；
- 需要修改编译器、看诊断和补全时；
- 需要发布包时。

只有验证自举、排查两个编译器差异，或研究“编译器自己编译自己”时，才直接使用 `selfhost/编译器.csay`。自举构建仍然需要默认编译器先产出 Stage 1。

## 能不能转成 C#

可以“写一个 C# 后端”，但不是现在的功能，也不是把源文件另存为 `.cs` 那么简单。

要做的是在 AST 之后新增一个代码生成器，把 Csay 的语义映射到 C#：

- `整数` → `long`，`小数` → `double`，`文本` → `string`，`真假` → `bool`；
- 类、结构、接口、继承、泛型 → C# 对应结构；
- 列表、表 → `List<T>`、`Dictionary<K,V>`；
- 异常 → `Exception` 派生类型；
- 区域分配 → `IDisposable` / `using` 或自定义分配器；
- 委托、Lambda、闭包 → `Func<>` / `Action<>` 或自定义委托；
- `引` 多文件 → 多个 C# 文件或一个程序集。

这会得到一套独立的运行时和标准库映射，测试面很大。当前 C 后端的运行时、异常用 `setjmp/longjmp`、区域分配和字符串表示都不能直接复用。

“手选一段 Csay 转成 C#”不是现有编辑器的功能。编辑器只做 Csay 的编辑、检查和运行；没有“选中代码 → 生成 C#”的转换器。要做也只能做“整个程序的后端翻译”，局部翻译无法保证类型、控制流和运行时语义一致。

## C# + CoreCLR 与热更新

技术上可以做一个可选的托管后端：Csay → C# → .NET 程序集，由 CoreCLR 运行。这样能直接获得 .NET 的 GC、字符串、集合和跨平台支持。

但“主要支持热更”是另一个量级的需求：

- CoreCLR 的热更新依赖 `MetadataUpdateHandler`、可收集的 `AssemblyLoadContext` 和调试器/运行时配合；
- 不能热更类型布局、泛型实例、已 JIT 的活动方法等；修改范围受运行时限制；
- 需要把程序集加载、卸载、版本切换、状态迁移设计成宿主的一部分；
- 热更失败时要有回退，不能把正在运行的程序留在半更新状态；
- 这与当前“生成原生 exe”的模型不同，不能只换一个 C 编译器。

因此合理路线是：先有稳定的 C# 后端和托管运行时，再单独做热更宿主；而不是在现有 C 后端上直接加 CoreCLR。若目标只是“改代码后快速重启”，当前的 `--fast` + 自动重编译已经够快，成本远低于热更。

## 内存与泄漏

Csay 没有垃圾回收。普通堆分配（文本拼接、列表扩容、表、类对象、闭包环境）不会自动释放，进程结束时由操作系统回收。

现有的生命周期工具是[区域与内存](21-区域与内存.md)：

- `区域 { }` 在离开块时整块释放块内分配；
- 文本可以从区域返回，编译器会复制；
- 列表、表、类对象不能从区域返回，否则会悬垂；
- `保留()` 只把文本复制到区域外；
- `使用` 负责调用 `关闭()`，不是内存回收。

闭包环境目前也在堆上分配，不会自动释放；大量创建长期闭包会泄漏。普通对象在函数返回后也不会自动释放，除非放进区域或进程结束。

要“自动处理泄漏”，有三条路：

1. **继续手动 + 区域**：成本低，适合短进程、批处理、命令行工具；当前路线。
2. **引用计数**：能自动释放无环对象，但循环引用、并发和性能都要处理，运行时要大改。
3. **GC / 托管后端**：C# + CoreCLR 直接获得 GC，但等于换运行时和后端，见上一节。

在当前 C 后端上做保守 GC 也可以，但要扫描栈、区分指针、处理区域和 C 库交互，风险和收益不匹配。短期内应把“区域 + 明确生命周期”作为正式用法，并在文档里如实说明限制。

## 编辑器与文档工具

编辑器 `tools/editor.html` 由 `tools/editor.mjs` 提供服务：

- 工作区文件树、多标签、保存、运行、实时检查；
- 输入 `对象.` 时按类型列出字段和方法；
- 右键“转到定义 / 查找引用 / 复制”，F12 / Shift+F12；
- 项目文件 `项目.csayproj` 与一键打包，产物在 `dist/`；
- 问题面板可跨文件跳转；
- F1 打开教程，教程侧栏支持章节/小节搜索。

符号索引在 `tools/符号索引.mjs`：按 `引` 递归加载文件，解析声明、成员、局部变量、参数和 Lambda 参数；模块名上的“转到定义”直接指向被引文件。引用搜索限制在工作区，跳过 `build`、`release`、`tools` 等目录，最多 500 个文件、200 个结果。

文档站 `tools/docs.mjs` 会把教程和参考文档一起渲染，标题生成稳定锚点，Markdown 里的 `.md` 链接会改写成站内 `/docs/<id>` 链接并保留 `#锚点`。新增文档时用 `[标题](文件名.md#锚点)` 就能跨页跳转。

## 发布给别人

发布分两种：

- 只运行程序：用编辑器“打包”生成的 `dist/<输出名>-<版本>.zip`，里面是 exe、源码、项目文件和 `README.txt`。对方解压后双击 exe 即可，不需要安装 Csay 或 C 编译器。
- 让对方也能写 Csay：发 `release/Csay-0.1.0-win64.zip`，里面是安装脚本、编辑器、命令行、随包 TCC、教程和示例。解压后双击 `安装Csay.bat`，脚本会安装到用户目录并把 `csay` 加入 PATH。

两种包都面向 64 位 Windows。未签名的 exe 第一次运行可能触发 SmartScreen，需要对方选择“更多信息 → 仍要运行”。

## 怎样选择

- 写程序、做项目、用测试/格式化/调试：默认编译器。
- 验证语言自举、比较两个编译器输出：自举编译器。
- 需要 GC、C# 生态、CoreCLR 热更：这是新后端项目，不是当前编译器的开关。
- 需要减少泄漏：先用区域和明确生命周期；不要期待当前运行时自动回收。

## 小结

- 当前是 Csay → C → 原生 exe，默认编译器用 TypeScript/Node，自举编译器用 Csay。
- 默认编译器覆盖完整工具链；自举编译器用于验证自举。
- C# 后端和 CoreCLR 热更都需要独立后端与运行时，不是现有功能。
- 没有 GC；区域是当前的生命周期工具，闭包环境也不会自动释放。
- 编辑器提供类型补全、转到定义、查找引用和跨文件问题跳转。
